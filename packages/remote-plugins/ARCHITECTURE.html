@aryagg/remote-plugins

A from-zero explainer, written for the next developer who opens this folder cold — one real running example (a Profile Card widget) carried through the whole thing.

TL;DR

This package lets your app load and mount a UI that a different team built and deployed separately — without npm install-ing it, without rebuilding when they ship. The whole engine is one function: mountRemotePlugin(manifest, target, context). Everything below either explains that one function, or shows you how to build something it can load. If you just want to build a plugin right now, skip to section 9.

1 The idea, in one picture

Say you're building a user directory. When someone clicks "View profile," you want to show a Profile Card — but that card is built and deployed by a different team, on their own schedule, maybe in a different framework entirely. You don't want to npm install their code and rebuild your whole app every time they change a button color.

YOUR APP (host)                          PROFILE-CARD TEAM's deploy
────────────────                          ───────────────────────────
                                            profile-card-entry.js
                                            (built & hosted on ITS OWN, separately)

mountRemotePlugin(manifest, el, ctx)
        │
        │   import(manifest.entryUrl)  ──────────▶  fetched live, over the network, at runtime
        │   ◀──────────────────────────────────────  module.mount(el, ctx)
        ▼
  { update, destroy }        ← you hang onto this: call update() when the user/theme changes,
                                call destroy() when the card closes

The line of code that makes this possible is one line, in loader.ts:

const module = await import(/* @vite-ignore */ url);

That's a live, dynamic import() resolved at runtime from a URL — not a static one resolved at build time. It's also why the package's own package.json only publishes src/lib: nothing else in this repo ever needs to reach the consumer.

The analogy

Your own component library is a dish you cook yourself, from your own kitchen's ingredients. A remote plugin is food delivery: the profile-card team's kitchen (their own deploy) cooks the dish (a JS module) and hands it to you fully wrapped (a mount() function). You just supply a table (the target element) and a walkie-talkie to the delivery person (context + bus).

Without this package, "embed someone else's UI" usually means one of three compromises:

ApproachThe catch
Publish an npm packageYou install & rebuild every time they ship — tight coupling, slow iteration.
Use an <iframe>Full isolation, but painful cross-window messaging and styling.
Hand-roll a dynamic import()Works, but no shared contract, no safety net if the remote code misbehaves, no standard teardown.

This package is a fourth option, done once, correctly: a tiny typed contract (manifest / context / module / instance) plus one function — mountRemotePlugin() — that does the load–validate–mount–wrap dance safely, every time.

2 The contract both sides agree to

Everything in src/lib/types/ is pure interfaces/enums — no logic, just the vocabulary both the host and the remote plugin must speak. For our Profile Card: the manifest says where to fetch it, the context carries the current user/theme, and whatever the profile-card team ships must export a mount() shaped exactly like module and instance require.

FileDefinesPurpose
manifest.tsIRemotePluginManifest, ERemoteAppEventDescribes a plugin before it's loaded (id, name, entryUrl)
context.tsIRemotePluginContext, IHostInfo, IRemotePluginUserThe API object the host hands the plugin every mount/update — theme, user, locale, navigate(), bus
events.tsIRemotePluginBusShape of the pub/sub channel: emit, on, unsubscribe, clear
module.tsIRemotePluginModuleWhat the downloaded JS file must export: mount(target, context)
instance.tsIMountedRemotePluginWhat the host gets back: update() and destroy()

The one rule the whole system boils down to

From the bottom of module.ts: "A remote plugin, at the end of the day, is any JavaScript file that exports a mount() function matching that shape. It could be built in React, Vue, vanilla JS — the host doesn't care."

3 How a mount actually happens

This is entirely host/runtime.ts — one function, mountRemotePlugin(manifest, target, context), running four steps (the source comments literally number them):

mountRemotePlugin(manifest, target, context)
│
├─ 1. VALIDATE   manifest.entryUrl must exist, or throw — before touching the network at all
│
├─ 2. LOAD       loadRemotePlugin(manifest.entryUrl)
│                 └─ import(url) — a real network fetch
│                 └─ accepts module.mount OR module.default (from defineRemotePlugin)
│                 └─ else throw "must export mount()"
│
├─ 3. MOUNT      remoteModule.mount(target, context)
│                 ├─ wrapped in try/catch → rethrown with the plugin's name in the message
│                 └─ result must have .destroy (function), or throw
│
└─ 4. WRAP       returns { update, destroy } where
                  update()  is a no-op once destroyed
                  destroy() runs once (guarded), calls instance.destroy(), then context.bus.clear()

Nothing here is a class — mountRemotePlugin is a plain async function returning a plain object closure. The destroyed boolean lives inside that closure; that's the hidden state guarding against double-destroy.

4 Talking to each other: context vs bus

There are exactly two channels between host and plugin, both living on the same context object, behaving completely differently.

1. context — host → remote (one-way, snapshot)

The host builds a plain object (theme, locale, params, user, navigate(), bus) and hands it to the plugin on mount, then again on update() whenever something changes. Think of it like props being passed down — the plugin only reads it, it can't write back through context.

2. bus — host ↔ remote (two-way, event-based)

Both sides hold the same bus instance. Either side can emit, the other on-listens. This is real code from the Profile Card, not an invented example — the "Follow" button inside the plugin:

// ProfileCard.svelte — inside the REMOTE plugin
const handleFollow = () => {
  user.isFollowed = !user.isFollowed;
  context?.bus.emit('UPDATE_FOLLOW', user);
};

...and the host side that reacts to it, passed in as the handlers prop of the wrapper component (more on this in section 6):

// +page.svelte — inside the HOST, wired to <RemotePlugin handlers={...}>
const profileCardHandlers = {
  UPDATE_FOLLOW: (userToUpdate) => updateKey(userToUpdate, 'isFollowed'),
  UPDATE_FOLLOWERS: (userToUpdate) => updateKey(userToUpdate, 'followers'),
};

The mental model

context = a snapshot the host refreshes and re-sends — good for things the remote just needs to know (theme, locale, params). bus = a shared walkie-talkie — good for anything that's a request, a response, or an event at an arbitrary moment (asking for data, saving state, a button click the host must react to).

No HTTP call, no global variable, no window.postMessage anywhere in this code. The plugin and host share the same JS realm (it's a dynamic import(), not an iframe) — context and its embedded bus are the only sanctioned channels between them.

5 Every file & function

remote-plugins/src/lib/                ← THE ACTUAL PUBLISHED LIBRARY (only this ships)
├── types/                             pure interfaces/enums — section 2
├── host                                ← code that runs INSIDE THE HOST APP
│   ├── bus.ts, loader.ts, runtime.ts, stylesheet.ts
└── remote                              ← code a PLUGIN AUTHOR imports
    └── definePlugin.ts

The dividing line that matters most: lib/host vs lib/remote. A remote plugin must only ever import from lib/remote and lib/types, never lib/host — that's not enforced by a linter, just convention plus file layout, but it's the core architectural boundary of the whole package.

FunctionFileWhat it does
createRemotePluginBus()bus.tsBuilds one pub/sub instance (Map<event, Set<handler>>). emit copies the handler Set to an array first so a handler that (un)subscribes mid-emit can't corrupt it. clear() nukes every handler — called once on destroy.

6 Trace a real example: opening the Profile Card

This is the actual flow in zhalia.core.ui today — real files, real function calls, no invented demo. A user clicks "View profile" on a row in a data table:

  1. user = row is set, which opens a <Modal> containing <RemotePlugin manifest={profileCardRemoteManifest} params={user} handlers={profileCardHandlers} />.
  2. RemotePlugin.svelte's onMount fires: ensurePluginStylesheet(manifest) links profile-card-entry.css, then calls mountPlugin().
  3. createRemotePluginBus() builds the bus. handlers (UPDATE_FOLLOW, UPDATE_FOLLOWERS) are registered with bus.on(...) before anything is mounted — this ordering matters, see section 7.
  4. buildRemoteContext(bus, params) assembles context — theme, locale, the clicked user as params, and the bus.
  5. mountRemotePlugin(manifest, container, context) runs → import('http://localhost:5175/profile-card-entry.js'), a real network fetch.
  6. Inside that file, ProfileCard.svelte mounts via Svelte's own mount(), rendering from context.params — the user that was clicked.
  7. User clicks "Follow" → the plugin calls context.bus.emit('UPDATE_FOLLOW', user) (section 4's real snippet).
  8. zhalia's profileCardHandlers.UPDATE_FOLLOW fires → updates the table's local state → the UI reflects it instantly, no page reload, no reaching into the host's internals.
  9. Modal closes → onDestroy calls handle.destroy() → the plugin's own destroy() unmounts its Svelte tree, then the bus is cleared.

That's the entire round trip: one URL, one mount call, one bus, one destroy. Section 9 walks through building this project from an empty folder.

7 Gotchas

Register bus listeners before you mount, not after

A plugin can emit its own "ready"-style event synchronously inside mount(), before mountRemotePlugin()'s promise even resolves. Register bus.on(...) first (like RemotePlugin.svelte does in step 3 of section 6) — register it after await mountRemotePlugin(...) and you silently miss that first event.

A few other things worth knowing that aren't obvious from reading the API surface:

  • loadRemotePluginCached is unused by mountRemotePlugin. runtime.ts calls the uncached loader directly — repeat mounts of the same URL are not deduped unless you call loadRemotePluginCached yourself. (Native import() already dedupes identical URLs at the module-graph level, so this mostly saves redundant shape-validation, not redundant fetches.)
  • Most of ERemoteAppEvent is vocabulary, not working features. The enum lists 20 event names, but the bus is fully generic and doesn't special-case any of them — a real host/plugin pair has to implement the request/response logic itself (e.g. SAVE_STATE → STATE).
  • destroy() is idempotent, update() is a silent no-op post-destroy. Neither throws after teardown — deliberate, but it means a stray update() after destroy() fails silently rather than loudly.
  • update is optional on your plugin's own return value, mandatory on the wrapped controller. Omit it and controller.update() just does nothing (instance.update?.(nextContext)).
  • Returning an object without destroy() throws immediately: "...mount() did not return an instance with destroy()".
  • Your plugin's own DOM/listeners are your responsibility. The runtime only guarantees bus.clear() — anything you attached (click listeners, timers) needs cleanup inside your own destroy().
  • Reusing the same target element for a second plugin without destroying the first just appends alongside it — nothing clears target for you.

8 Mental model to explain this to someone else

remote-plugins is a two-drawer toolbox plus one function that connects them.

  • Drawer 1 — types/: the paperwork both sides agree to before anything runs (section 2).
  • Drawer 2a — host/: tools for whoever is hosting a plugin — a bus, a loader, and mountRemotePlugin(), which chains "validate → load → mount → wrap safely" and hands back a {update, destroy} remote control.
  • Drawer 2b — remote/: one convenience helper, defineRemotePlugin(), for whoever is writing a plugin.

If you strip away comments and types, the entire runtime behavior is ~25 lines in runtime.ts and ~25 lines in bus.ts. Everything else is contract (types), convenience (defineRemotePlugin), or an app that actually uses it (section 6 & 9).

9 Build your own — a from-scratch walkthrough

Everything above explains how the machinery works. This is the opposite: a straight-line recipe for going from an empty folder to a plugin showing up inside zhalia.core.ui — and it's not hypothetical. The Profile Card from section 6 is backed by exactly this recipe, in a real project called my-remote-plugin: its own repo, its own package.json, its own git history.

The two halves

Part A happens in your own new folder, completely separate from zhalia.core.ui — you write a plugin and build it into one JS file. Part B happens inside zhalia.core.ui — you tell it that file exists and drop a component on a page to mount it. Nothing in Part A imports anything from zhalia; nothing in Part B imports your plugin's source. The only thing connecting them is a URL.

Part A — create the remote app

A1. Scaffold the folder

A remote plugin isn't a SvelteKit app or a page — it's a tiny standalone project whose job is to build down to one JS file per plugin. Framework is your choice; the host only ever sees your build output. Run this from wherever you keep projects — it doesn't need to live inside this monorepo:

npm create vite@latest my-remote-plugin -- --template svelte-ts
cd my-remote-plugin
npm install

Keep the whole scaffold — src/main.ts, src/App.svelte, index.html, vite.config.ts. npm run dev still serves App.svelte as a normal page, so you always have a plain browser preview of your plugin with zero host involved. You're adding to this scaffold, not replacing it.

A2. Add the dependency and write the plugin's UI

Inside this monorepo, link it for real type-checking and defineRemotePlugin() autocomplete:

npm install @aryagg/remote-plugins@file:../remote-plugins

Building this outside the monorepo entirely?

@aryagg/remote-plugins is "private": true and isn't published to a registry, so a fully separate repo can't npm install it the normal way. That's exactly why the contract is hand-writable (section 2's "one rule") — export a plain { mount(target, context) { ... return { update, destroy }; } } with no dependency at all, and it works identically. Everything below just adds nicer typing on top of the same shape.

Write your plugin as a normal Svelte component that knows nothing about being remote, then a thin mount file that wraps it. This is the real pattern behind the Profile Card — a small reactive "context box" plus defineRemotePlugin:

// src/lib/remote-plugin/context.svelte.ts — the reactive bridge
// (runes work here because the filename ends in .svelte.ts)
import type { IRemotePluginContext } from '@aryagg/remote-plugins';

export function createRemoteContext(initial: IRemotePluginContext | null = null) {
  let context = $state(initial);
  return {
    get current() { return context; },
    set(next: IRemotePluginContext) { context = next; }
  };
}
<!-- src/lib/MyWidget.svelte — ordinary Svelte, no idea it's "remote" -->
<script lang="ts">
  import type { createRemoteContext } from './remote-plugin/context.svelte';
  import type { IRemotePluginContext } from '@aryagg/remote-plugins';

  let { remoteContext }: { remoteContext: ReturnType<typeof createRemoteContext> } = $props();
  const context: IRemotePluginContext | null = $derived(remoteContext.current);
</script>

<h2>Hello, {context?.user?.name ?? 'guest'}</h2>
<p>Theme: {context?.theme}</p>
// src/lib/remote-plugin/mountMyWidget.ts — the actual "door" the host calls
import { mount as svelteMount, unmount as svelteUnmount } from 'svelte';
import { defineRemotePlugin } from '@aryagg/remote-plugins';
import MyWidget from '../MyWidget.svelte';
import { createRemoteContext } from './context.svelte';
// Pulls Tailwind into THIS entry's own build graph — build.lib.entry only
// bundles what each entry file actually imports.
import '../../app.css';

export default defineRemotePlugin((target, context) => {
  const remoteContext = createRemoteContext(context);
  const app = svelteMount(MyWidget, { target, props: { remoteContext } });

  return {
    update(nextContext) { remoteContext.set(nextContext); },
    async destroy() { await svelteUnmount(app); }
  };
});

Why the context box instead of passing context straight through as a prop: the host doesn't hand your plugin a context once — it calls update(nextContext) repeatedly (theme toggles, params change). A plain variable swap gives Svelte no signal to re-render; wrapping it in $state(...) makes each update() actually redraw the component, while the remoteContext prop itself keeps the same reference for the component's whole life.

A3. Make it buildable — the real, multi-plugin vite.config.ts

A single project can build several independent plugins — one mount*.ts file per plugin, each its own standalone bundle the host loads separately. This is my-remote-plugin's actual config, building three entries at once (Profile Card is one of them):

// vite.config.ts
import { defineConfig } from 'vite';
import { svelte } from '@sveltejs/vite-plugin-svelte';
import tailwindcss from '@tailwindcss/vite';

export default defineConfig({
  plugins: [tailwindcss(), svelte()],
  // Cross-origin dynamic import() of an ES module always goes through a
  // CORS-mode fetch (unlike classic scripts), so the host (a different
  // origin/port) can't load these entries unless this server sends
  // Access-Control-Allow-Origin. Fixed port so the host's manifest URLs
  // stay stable across restarts.
  preview: { port: 5175, strictPort: true, cors: true },
  build: {
    // All entries share one app.css instead of per-entry stylesheets —
    // cssCodeSplit:true made Rollup's chunk-naming fall back unpredictably
    // whenever two entries' compiled CSS overlapped.
    cssCodeSplit: false,
    lib: {
      entry: {
        'profile-card-entry': 'src/lib/remote-plugin/mountProfileCard.ts',
        'follow-display-entry': 'src/lib/remote-plugin/mountFollowDisplay.ts',
        'say-hi-service': 'src/lib/remote-plugin/mountHi.ts'
      },
      formats: ['es'],
      fileName: (_format, entryName) => `${entryName}.js`
    },
    rollupOptions: {
      output: {
        assetFileNames: (asset) =>
          asset.names?.[0]?.endsWith('.css') ? 'remote-plugin.css' : '[name][extname]'
      }
    }
  }
});

build.lib only affects vite build — npm run dev still serves App.svelte untouched, so you keep a normal dev preview alongside the production bundles.

A one-file entry doesn't need a Svelte component at all

say-hi-service above points at a file that just exports a plain function — no defineRemotePlugin, no mount(), no UI:

// src/lib/remote-plugin/mountHi.ts
export const sayAlertHi = (name: string) => alert('Say Hi ' + name);

That's the non-UI pattern from Part B5 below — the host calls loadRemoteManifestFile() on this entry's URL and just uses whatever it exports, no mounting involved.

npm run build → dist/profile-card-entry.js, dist/follow-display-entry.js, dist/say-hi-service.js, plus the shared dist/remote-plugin.css.

A4. Serve it so zhalia.core.ui can reach it

During development, npm run dev — my-remote-plugin's package.json pins this to "dev": "vite --port 5175" — so http://localhost:5175/profile-card-entry.js responds. 5175 isn't arbitrary: it's zhalia's default PUBLIC_REMOTE_PLUGIN_BASE_URL (Part B1). In production this is wherever you actually deploy dist/ — a static host or CDN.

Part B — connect it inside zhalia.core.ui

B1. Declare the manifest

Every plugin zhalia knows about is a plain IRemotePluginManifest object in src/lib/shared/connected-apps/manifest.ts — no database, no admin screen, just a TypeScript file:

// src/lib/shared/connected-apps/manifest.ts
import { PUBLIC_REMOTE_PLUGIN_BASE_URL } from '$env/static/public';
import type { IRemotePluginManifest } from '@aryagg/remote-plugins';

export const profileCardRemoteManifest: IRemotePluginManifest = {
  id: 'profile-card-entry',
  name: 'Profile Card',
  version: '0.0.0',
  entryUrl: `${PUBLIC_REMOTE_PLUGIN_BASE_URL}/profile-card-entry.js`,
};
FieldWhat it actually does
idA unique label for your own code — the library itself never reads it.
nameShown in every error this library throws (e.g. "Remote plugin 'Profile Card' threw while mounting…") — make it recognizable.
versionDocumentation only right now — nothing checks it.
entryUrlThe one field that matters at runtime — must resolve to your built JS file.

PUBLIC_REMOTE_PLUGIN_BASE_URL comes from zhalia's .env (default http://localhost:5175) — one base URL shared by every plugin manifest, just a different filename per plugin.

B2. Mount it on a page — the easy way

zhalia already has a generic wrapper that does createRemotePluginBus() → ensurePluginStylesheet() → build context → mountRemotePlugin() → destroy()-on-unmount for you: RemotePlugin.svelte. This is the exact call from section 6:

<RemotePlugin
  manifest={profileCardRemoteManifest}
  params={user}
  handlers={profileCardHandlers}
/>

params becomes context.params inside the plugin — whatever it needs to know about where it's mounted.

B3. Mount it yourself — the manual way

Only needed if RemotePlugin.svelte doesn't fit your case — this is exactly what it does internally:

import { createRemotePluginBus, ensurePluginStylesheet, mountRemotePlugin } from '@aryagg/remote-plugins';
import { buildRemoteContext } from '$shared/connected-apps/context';

ensurePluginStylesheet(manifest);
const bus = createRemotePluginBus();
const context = buildRemoteContext(bus, params);
const handle = await mountRemotePlugin(manifest, containerEl, context);

// later, when something changes:
handle.update(buildRemoteContext(bus, params));

// when the container goes away:
await handle.destroy();

B4. React to plugin events — handlers

RemotePlugin.svelte's handlers prop maps a bus event name to a function — each entry becomes a bus.on(event, handler) call before mounting (section 6, step 3). The event names and payloads are a private agreement between your plugin and whatever page mounts it; the wrapper and the library don't know or care what they mean.

B5. Non-UI plugins — no mount() at all

Not every remote file needs to render anything. If it just exports plain functions, skip mountRemotePlugin and use the lower-level loader directly — this is the real say-hi-service plugin from A3:

import { loadRemoteManifestFile } from '@aryagg/remote-plugins';

const utilityModule = await loadRemoteManifestFile(sayHiRemoteManifest.entryUrl);
// null if the file 404s, fails to parse, or the URL is unreachable
utilityModule?.sayAlertHi('World');

Pair this with isManifestUrlLoaded(url) (a thin zhalia-only wrapper around loadRemotePlugin) to probe reachability before showing UI that depends on a plugin — e.g. hiding a menu action if it isn't deployed yet.
