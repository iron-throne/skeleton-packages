@aryagg/remote-plugins

A from-zero explainer of this package only — what it does, how it's built, and how the pieces fit together. Written for the next developer who opens this folder cold.

1 What this package is for

@aryagg/remote-plugins is a small library, not an app. It lets a "host" web page load a piece of UI that was built and shipped separately — possibly by a different team, on a different deploy, in a different framework — and mount it into a <div>, without the host needing to know how that UI was built.

Look at package.json:

"exports": {
  ".": { "types": "./src/lib/index.ts", "default": "./src/lib/index.ts" }
}

Only src/lib is published. Everything else in the folder (App.svelte, main.ts, demo/) is a dev sandbox that exists purely so you can see the library work without standing up a second server. It never ships.

2 Why it exists

Normal component libraries require the consumer to npm install them and bundle everything together at build time. Every "plugin" has to be known and compiled in ahead of time.

This package solves a different problem: loading UI you didn't compile in, decided at runtime, from a URL. That's what this one line in loader.ts does:

const module = await import(/* @vite-ignore */ url);

That's a live, dynamic import() — not a static one resolved at build time.

Analogy

A normal library is a dish you cook yourself from your own kitchen's ingredients. A remote plugin is food delivery — someone else's kitchen (a separate deploy) cooks the dish (a JS module) and hands it to you fully wrapped (a mount() function). You just supply a table (the target element) and a way to talk to the delivery person (the context + bus).

3 The problem it solves, concretely

Without this package, embedding "someone else's UI" into your app means one of:

  • They publish an npm package, you install & rebuild every time they ship — tight coupling, slow iteration.
  • You use an <iframe> — full isolation, but painful cross-window messaging and styling.
  • You hand-roll a dynamic import() yourself, with no shared contract for what gets passed in/out, no safety net if the remote code misbehaves, and no standard way to tear it down cleanly.

This package is the third option, done once, correctly: a tiny, typed contract (manifest / context / module / instance) plus one function, mountRemotePlugin(), that does the load–validate–mount–wrap dance safely every time.

4 How it works internally — the shape of the contract

Everything in src/lib/types/ is pure interfaces/enums — no logic, just the agreed vocabulary both the host and the remote plugin must speak.

FileDefinesPurpose

context.tsIRemotePluginContext, IHostInfo, IRemotePluginUserThe API object the host hands the plugin every mount/update — theme, user, locale, navigate(), bus

The one rule the whole system boils down to

From the bottom of module.ts: "A remote plugin, at the end of the day, is any JavaScript file that exports a mount() function matching that shape. It could be built in React, Vue, vanilla JS — the host doesn't care."

5 How plugins are loaded, validated, mounted, and returned

This is entirely host/runtime.ts — one function, mountRemotePlugin(manifest, target, context), running four numbered steps (the source comments literally number them):

mountRemotePlugin(manifest, target, context)
│
├─ 1. VALIDATE MANIFEST (before touching network)
│     └─ manifest.entryUrl must exist          → else throw
│
├─ 2. LOAD
│     └─ loadRemotePlugin(manifest.entryUrl)
│          └─ import(/* @vite-ignore */ url)   ← dynamic ES import, real network fetch
│          └─ accept module.mount OR module.default (from defineRemotePlugin)
│          └─ else throw "must export mount()"
│
├─ 3. MOUNT
│     └─ remoteModule.mount(target, context)
│          ├─ wrapped in try/catch → rethrown with plugin name in the message
│          └─ result must have .destroy (function) → else throw
│
└─ 4. WRAP into a safe controller
      └─ returns { update, destroy } where:
           - update(): no-op if already destroyed
           - destroy(): guarded to run only once,
                         calls instance.destroy(), then context.bus.clear()

Nothing here is a class — mountRemotePlugin is a plain async function returning a plain object closure. The destroyed boolean lives inside that closure; that's the hidden state guarding against double-destroy.

6 How this package talks to the rest of the system

There are exactly two channels between host and plugin, and they serve different purposes. Both live on the same context object the host constructs, but they behave completely differently.

1. context — host → remote (one-way, snapshot)

The host builds a plain object (IRemotePluginContext: theme, locale, params, user, navigate(), bus) and hands it to the plugin on mount, then again on update() whenever something changes:

// host: RemotePluginMount.svelte
handle = await mountRemotePlugin(manifest, container, context);
// later, when locale/params change:
handle.update(buildRemotePluginContext({ bus, params }));

Think of it like props being passed down. The remote plugin only reads it — there's no way for the remote to write back through context. That's why close was removed from the type: a plain value can't be a two-way channel, and it duplicated what the bus already does (ERemoteAppEvent.CLOSE).

2. bus — host ↔ remote (two-way, event-based)

Both sides hold the same bus instance — it's part of the context object. Either side can emit an event, the other side listens:

// interface, for reference
emit(event: string, payload?: unknown): void
on(event: string, handler: (payload?: unknown) => void): () => void

Remote → host (remote wants something from host):

// inside the remote plugin
context.bus.emit('request_host_data', { key: 'userPrefs' });
context.bus.on('host_data', (payload) => {
  console.log('got data from host:', payload);
});

// host side, already wired in RemotePluginMount.svelte
localBus.on(ERemoteAppEvent.REQUEST_HOST_DATA, (payload) => {
  const { key } = payload;
  localBus.emit(ERemoteAppEvent.HOST_DATA, { key, value: /* real data */ });
});

Host → remote (host wants to push something in, unprompted):

// host side
localBus.emit(ERemoteAppEvent.HOST_EVENT, { announcement: 'new feature!' });

// remote side
context.bus.on('host_event', (payload) => {
  // react to it
});

The mental model

context = a snapshot the host refreshes and re-sends — good for things like theme/locale/params that the remote just needs to know. bus = a shared walkie-talkie — good for anything that's a request, a response, or an event that happens at an arbitrary moment (asking for data, saving state, resizing, closing, custom app events).

Anything that used to go through a one-off field like close on context can always be done as a bus event instead — that's why removing it didn't lose any capability, just a redundant second path to the same outcome.

No HTTP call, no global variable, no window.postMessage anywhere in this code. The plugin and host share the same JS realm (it's a dynamic import(), not an iframe); context and its embedded bus are the only sanctioned channels between them.

8 Every function / module, in plain English

createRemotePluginBus() — bus.ts

Factory that builds one pub/sub instance. Internally: Map<eventName, Set<handler>>.

  • emit(event, payload) — copies the handler Set to an array first, then iterates, so a handler that subscribes/unsubscribes mid-emit can't corrupt the live Set.
  • on(event, handler) — adds to the Set, returns an unsubscribe closure (the primary way to unsubscribe — no need to keep the handler reference around).
  • unsubscribe(event, handler) — manual removal if you kept the handler reference.
  • clear() — nukes every handler for every event. Called once by mountRemotePlugin's destroy().

loadRemotePlugin(url) — loader.ts

Does the actual import(url), then normalizes the result: accepts either export const mount = ... (named) or export default defineRemotePlugin(...) (default). Throws if neither shape is found.

loadRemotePluginCached(url) — loader.ts

A memoizing wrapper around the above, keyed by URL in a module-level Map<string, Promise<...>>. If the promise rejects, it deletes itself from the cache so a later call can retry.

Not currently used by mountRemotePlugin — see section 12.

mountRemotePlugin(manifest, target, context) — runtime.ts

The orchestrator described in section 5: validate → load → mount → wrap.

defineRemotePlugin(setup) — definePlugin.ts

A one-line identity-ish helper: (setup) => ({ mount: setup }). Does nothing at runtime except give TypeScript autocomplete on target/context and guarantee the object shape the loader expects. Purely a DX helper for plugin authors — the host's loader would accept a hand-written { mount: ... } object just as well.

9 Data flow, step by step

Using the only real example in the package — App.svelte mounting exampleRemotePlugin.ts:

HOST (App.svelte)                              REMOTE (exampleRemotePlugin.ts)
──────────────────                              ───────────────────────────────
1. const bus = createRemotePluginBus()
2. bus.on(READY, ...) bus.on(CUSTOM_EVENT,...)   (must happen BEFORE step 4!)
3. build manifest { entryUrl }
4. await mountRemotePlugin(manifest, el, ctx) ─────▶ import(entryUrl)  (network/module fetch)
                                                  ◀── module resolved, .mount found
                                                  remoteModule.mount(target, context) runs:
                                                     - builds DOM, appends to target
                                                     - reads context.theme/user → renders
                                                     - wires button clicks → context.bus.emit(...)
                                                     - context.bus.emit(READY)  ───────┐
5. bus fires READY handler ◀──────────────────────────────────────────────────────────┘
                                                     returns { update, destroy }
6. mountRemotePlugin wraps it, returns controller
7. controller stored; mounted = true

--- user clicks "Toggle theme" ---
8. toggleTheme() rebuilds context, calls controller.update(newContext)
                                                  ──▶ instance.update(nextContext) → re-renders text

--- user clicks "Send an event to host" (inside the plugin's own UI) ---
                                                  plugin: context.bus.emit(CUSTOM_EVENT, {...})
9. bus fires CUSTOM_EVENT handler → appendLog(...)

--- user clicks "Destroy plugin" ---
10. controller.destroy()
                                                  ──▶ instance.destroy(): removes listeners, removes DOM
11. context.bus.clear()   (all handlers gone)

Gotcha called out in the code itself

The plugin emits READY synchronously inside its own mount(), which runs before mountRemotePlugin()'s promise resolves (App.svelte, around lines 71–76). If you register bus.on(READY, ...) after await mountRemotePlugin(...), you silently miss that first event. Listeners must be registered first.

10 Real-world example of usage

Picture a company dashboard (the host). A separate team ships a "billing widget" as its own deployed bundle at https://billing.example.com/widget/v2/entry.js. The host never installs that team's code as an npm dependency — it just does:

const manifest: IRemotePluginManifest = {
  id: 'billing-widget',
  name: 'Billing Widget',
  version: '2.0.0',
  entryUrl: 'https://billing.example.com/widget/v2/entry.js',
};

const controller = await mountRemotePlugin(manifest, containerEl, {
  apiVersion: 1,
  host: { id: 'dashboard', name: 'Main Dashboard' },
  user: currentUser,
  theme: currentTheme,
  locale: 'en',
  params: {},
  navigate: (path) => router.push(path),
  bus,
});

The billing team can redeploy their widget independently — the dashboard doesn't rebuild, doesn't even know the widget changed, as long as it still exports a compatible mount(). That decoupling — separate deploy, shared-at-runtime contract — is the entire value proposition of this package.

11 What happens internally when a plugin is mounted

Concretely, in order, inside mountRemotePlugin:

  1. The entryUrl guard runs synchronously — zero network cost if the manifest is malformed.
  2. await import(url) — the browser/Vite fetches and evaluates the remote module. This is where an unreachable URL, a 404, or a syntax error in the remote file would throw.
  3. Shape-check on the resolved module (typeof module.mount === 'function'), checking both named and default export.
  4. remoteModule.mount(target, context) executes the plugin's own setup code — inside a try/catch so a throwing plugin doesn't produce a stack trace pointing at your host code; it's rethrown with the plugin's name prefixed.
  5. Shape-check on what mount() returned (must have .destroy).
  6. A fresh closure-scoped destroyed flag is created, and the {update, destroy} controller object is returned to the caller.

12 Hidden / non-obvious logic worth knowing

loadRemotePluginCached is effectively dead code from mountRemotePlugin's perspective

runtime.ts imports and calls the uncached loadRemotePlugin directly. The cached version is exported from the barrel and available to a host app that wants to call it manually, but the main entry point doesn't use it — repeat mounts of the same URL are not deduped by this library unless you call loadRemotePluginCached yourself. (Note: native import() on an identical URL is already deduped by the JS engine's module graph, so re-importing the same entryUrl mostly doesn't re-run top-level code anyway — the cache mainly saves you from redundant shape-validation and redundant in-flight requests, not redundant fetches.)

Most of ERemoteAppEvent is unimplemented plumbing

The enum lists 20 event names (SAVE_STATE/STATE, REQUEST_HOST_DATA/HOST_DATA, PERMISSION_REQUEST/PERMISSION_RESPONSE, etc.), but the bus itself is generic (emit(event: string, payload?: unknown)) and doesn't special-case any of them. Only READY, NAVIGATE, and CUSTOM_EVENT are actually wired up anywhere in this package (in the demo). The rest are a shared vocabulary, not working features — a real host/plugin pair has to implement the request/response logic for e.g. SAVE_STATE → STATE themselves.

destroy() is idempotent, update() is a silent no-op post-destroy

Calling either after teardown will not throw, it just does nothing. Deliberate defensive design — but it means a bug that calls update() after destroy() fails silently rather than loudly. Worth remembering when debugging "why doesn't my context update reach the plugin."

update() is optional on the raw module, mandatory on the wrapped controller

A plugin's own mount() doesn't have to return update — the runtime only checks for destroy. If a plugin omits update, calling controller.update() just does nothing (optional chaining: instance.update?.(nextContext)), no error.

13 Common mistakes developers make with this package

  1. Registering bus listeners after await mountRemotePlugin(...) — misses the synchronous READY event.
  2. Returning an object without destroy() from your plugin's mount() — throws immediately: "...mount() did not return an instance with destroy()".
  3. Forgetting to remove your own DOM/event listeners inside your plugin's destroy() — the runtime only guarantees its own teardown (bus.clear()); anything the plugin attached (like button click listeners) is the plugin author's responsibility to remove.
  4. Assuming mountRemotePlugin caches/dedupes loads — it doesn't (see section 12); calling it twice for the same URL re-runs the full load→mount pipeline twice.
  5. Reusing the same target element for a second plugin without destroying the first — nothing in runtime.ts clears target before mounting; a second mount() call just appends alongside the first plugin's DOM.

14 Mental model to explain this to someone else

remote-plugins is a two-drawer toolbox plus one function that connects them.

  • Drawer 1 — types/: the paperwork both sides agree to before anything runs — what a plugin declares about itself (manifest), what info/comms channel the host hands it (context + bus), and what shape the loaded code and its return value must have (module, instance).
  • Drawer 2a — host/: three tools for whoever is hosting a plugin — createRemotePluginBus() to make a walkie-talkie, loadRemotePlugin() to fetch-and-shape-check the remote code, and mountRemotePlugin() — the one function that chains "validate → load → mount → wrap safely" and hands back a {update, destroy} remote control.
  • Drawer 2b — remote/: one convenience helper, defineRemotePlugin(), for whoever is writing a plugin — wraps your setup function into { mount: setup } with type-checking.
  • The demo/ + App.svelte + main.ts files are not part of the toolbox — they're a stage play acting out both roles (host and remote) in one process, purely so you can watch the whole exchange happen without deploying anything.

If you strip away comments and types, the entire runtime behavior is ~25 lines in runtime.ts and ~25 lines in bus.ts. Everything else is contract (types), convenience (the defineRemotePlugin wrapper), or demonstration (the Svelte shell).
